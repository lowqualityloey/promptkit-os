## [Unreleased]

### Added
- **Onboarding provenance consistency fixtures (Issue #641 Scenario 6 follow-up)**: New deterministic fixture family `scripts/tests/fixtures/onboarding-provenance/` with paired Bash and PowerShell harnesses (`scripts/tests/run-onboarding-provenance-fixtures.sh` and `scripts/tests/run-onboarding-provenance-fixtures.ps1`) supplies the three inconsistency regressions Issue #641 Scenario 6 named but did not ship: a human-confirmed decision whose linked assumption is still recorded as open (`assumption-still-open`), an accepted default widened to settle an adjacent test-runner decision the human did not approve (`default-widened`), and intake metadata or obligation inconsistencies — a contradictory round count (`count-contradiction`), a question budget exceeded for the recorded interview size (`question-budget-exceeded`), a verification obligation with a missing owner plus an unresolvable destination (`obligation-untracked`), a structurally incomplete artifact that drops the verification-obligation register (`register-missing`), a register present as prose instead of the required table with its expected header and separator row (`register-not-tabular`), a register whose header row renames a column or reorders the columns it claims to carry (`header-renamed`, `header-reordered`), and an assumption whose linked decision does not exist in the Decisions register (`assumption-link-unresolved`). Register structure is checked as a complete ordered header row: every column name must match in name and position, not merely the first cell and the column count, and a malformed register suppresses the dependent semantic checks instead of emitting a cascade of follow-on diagnostics. Every parsed data row must also carry exactly the declared cell count for its register (Intake metadata 2, Decisions 4, Accepted defaults 6, Assumption records 8, Verification obligations 5, Round log 3); a short or over-wide row is rejected as `ROW_WIDTH` with the register, the expected and actual counts, and the leading identifying cell, and that register's dependent semantic checks are suppressed rather than reported against a row the checker cannot read. An assumption's `Linked decision` cell may hold a placeholder (blank, `-`, or `none`) meaning no link; anything else must match the `DECISION-<slug>-<nnn>` identifier syntax and name a decision present in the Decisions register, reported as `ASSUMPTION_LINK_INVALID` for a malformed value and `ASSUMPTION_LINK_UNRESOLVED` for a well-formed value with no matching row. Each case is a complete artifact set (the Intake Record plus the generated `docs/STATE.md`) checked against one shared TAB manifest (`expected/cases.tsv`) that pins the exact summary line and the complete normalized diagnostic set; `valid-baseline` is the positive control and every other case is a genuine negative control the harness must reject. Both harnesses also snapshot repository file hashes and `git status` per case and fail if they changed anything, and both fail closed when a case directory is missing from the manifest, a manifest row does not have exactly four tab-separated fields (including a trailing tab, a repeated tab that leaves an empty field, or a fifth field), a case name is empty, or a stated expected exit code is not numeric. Rules 1, 2 and 8 and derived baselines stay with the existing documentation-contract assertions and the bounded human review checklist. Both harnesses are wired into `PromptKit OS CI` on the existing Linux and Windows paths. Fixture and test-only: no protocol, workflow, template, authority-model, or runtime change; a green matrix proves these sixteen artifact shapes are classified as specified and does not prove that a live model produces consistent artifacts.

### Changed
- **Bounded CLI capability discovery — documentation only (issue #555)**: Clarify portable CLI selection in `protocols/setup.md` and the dependency-free provider baseline in `protocols/context-economy.md`: `grep`/`find` on POSIX-compatible shells and `Select-String`/`Get-ChildItem` on native Windows PowerShell are the environment-specific baselines, `rg`/`fd`/`bat` (and the `fdfind`/`batcat` binary names) are optional accelerators selectable on their effective flags, and any fallback preserves hidden/ignored-path, symlink, case, regex, and exit-status semantics with non-interactive, bounded output that never silently omits evidence needed for correctness, security, or verification. Documentation only: no executable capability detector, runtime enforcement, capability cache, or measured efficiency improvement is added.
- **Terminology consistency (issue #605)**: Clarify Adoption Stages 0–4, task-ceremony Levels 0–3, and the refactor workflow’s Level 0 boundary.
- **Installed-instruction integrity boundary (issue #602)**: Document the trust boundaries, guarantees, and residual risk across Git submodule, npm courier, and host-directive installation modes in `protocols/setup.md` and `docs/MIGRATION.md`, distinguishing archive/transport verification from post-install and host runtime execution.
