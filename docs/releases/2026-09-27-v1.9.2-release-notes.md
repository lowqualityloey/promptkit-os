## v1.9.1 Failed To Publish. Here's Why.

`v1.9.1` is tagged and has a GitHub release, but **no such version exists on npm.** The publish step returned `E404`. The run log tells the whole story: the job minted its OIDC token, signed a provenance statement, published it to the sigstore transparency log — and *then* got `404 Not Found - PUT https://registry.npmjs.org/promptkit-os`. So authentication was prepared correctly and the write was still attempted the wrong way.

**The cause was one line of workflow config.** The publish job passed `registry-url` to `actions/setup-node`, which is convenient, and which writes a userconfig `.npmrc` containing:

```
//registry.npmjs.org/:_authToken=${NODE_AUTH_TOKEN}
```

That entry is enough for npm to choose the **token** authentication path — even when `NODE_AUTH_TOKEN` is empty. npm never attempts the OIDC exchange. We had removed the token; we had not removed the *mechanism that looks for one*. Trusted publishing was live in the dashboard, working on paper, and never actually exercised.

**Nothing was lost.** `1.9.0` remains published and functional, so `npx promptkit-os` still resolves to a working courier, and the git submodule path is canonical regardless. The cost was a version number. The `v1.9.1` tag and its GitHub release are deliberately **kept** as the immutable record of the attempt; they are not being deleted or moved.

## The Fix: Remove The Mechanism, Then Assert On It

**No `registry-url`.** The publish job no longer asks setup-node to generate a registry `.npmrc`. Trusted publishing needs no registry configuration, so the input is simply gone. With no auth entry anywhere, npm has no token path to fall back to and takes the OIDC route.

**A release that would cheat now fails immediately.** A new `Assert No Token Auth Will Be Used` step runs *before* version sync, the tarball assertion, the smoke test, and the publish. It fails the job with an explicit message if `NODE_AUTH_TOKEN` or `NPM_TOKEN` is present in the job environment, or if `NPM_CONFIG_USERCONFIG` points at a file containing an auth entry. The old failure mode was a silent registry 404 after a full release run; the new one is a named error in the first minute, naming the exact condition and the exact fix.

**The guard is tested, not assumed.** All three states were exercised: a clean environment passes, a set `NODE_AUTH_TOKEN` fails, and an auth-bearing `.npmrc` fails.

## What Didn't Change

The npm `^11.5.1` pin (trusted publishing still gates on the npm CLI, not Node), `node-version: 20`, `permissions` (`contents: read` + `id-token: write`), the AC-1 smoke test running **before** publish, the minimal-tarball assertion, `--provenance`, and the AC-1 courier/canonical equivalence property. No protocol, template, installer, or directive changed; `init.sh` / `init.ps1` remain the single source of truth and `templates/agent-directive-template.md` is byte-unchanged. Consumers see nothing.
