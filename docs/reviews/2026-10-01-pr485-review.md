## Findings

### R1 [P2] Apply the legacy exemption to the record path field only

**Location:** .github/workflows/ci.yml:137; PowerShell equivalent:339.

The rewritten wrappers still discard any diagnostic containing `2026-09-08-v1.0.0-` anywhere in its full text. A newly added invalid record at docs/releases/new-record.md can use Evaluation ID `EVAL-2026-09-08-v1.0.0-new`. All of its missing-field and evaluation-mismatch diagnostics carry that ID in field two, so both wrappers discard them despite the new record's non-legacy path in field three. The validator exits1 with FAILED, and CI announces that all diagnostics are grandfathered.

The validators serialize category|evaluation-id|record-path|message|remediation (Bash:25–33; PowerShell:16–27). Their Evaluation ID parsing permits this value (Bash:667–668; PowerShell:102–103). Thus the current filter does not establish that an affected record is a historical exception. This is an unresolved part of the F14 hardening, not a claim that the broad substring filter was first introduced here.

**Correction:** Parse the diagnostic fields and exempt only the exact approved historical record paths. Keep all new-file diagnostics fatal even when an ID, message or referenced artifact mentions a historical record. Verify a mixed legacy/new failure, including a new record with the legacy prefix in its ID.

### R2 [P2] Validate the complete output contract before accepting a result

**Location:** .github/workflows/ci.yml:124–143; PowerShell equivalent:330–345.

The wrappers require only the presence of the expected summary prefix. On exit0, any VALID-prefixed line immediately permits success, even alongside failure diagnostics or unexpected errors. On exit1, a FAILED-prefixed line with no diagnostic rows also passes: the filtered error set is empty and is interpreted as "all diagnostics grandfathered". Unknown non-structured stderr mixed with the expected summary is silently ignored.

Unexpected runtime output is reachable without a special exit code: Bash enumerates records through a find process substitution (validator:689), and PowerShell uses Get-ChildItem with ordinary non-terminating error behavior (validator:601). An enumeration error can coexist with a normal summary. The changed wrappers' exit-code checks do not detect an error whose child process still emits that summary.

**Correction:** Parse all captured output and require one well-formed summary consistent with the process status and diagnostics. Reject unknown lines, contradictory summaries, exit0 with diagnostics, and exit1 without any recognized diagnostic. Accept exit1 only when every diagnostic resolves to an allowed legacy path. Cover actual wrapper acceptance with clean VALID, allowed legacy FAILED, new/mixed diagnostics, crash, unknown/empty output and inconsistent status/summary cases.
