## #465 — Valid, strengthen verification before implementation

[Issue #465](https://github.com/lowqualityloey/promptkit-os/issues/465)

The race, cookie guarantees and protected/public-endpoint distinction are accurately captured. The proposed acceptance criterion requires a concurrent result, but the verification section includes only reference validation and manual OWASP review. Those checks cannot establish atomicity of the example implementation.

Recommended acceptance and verification additions:

- Exercise two refresh calls concurrently using a deterministic barrier or transaction-capable fixture; assert at most one successor is created and reuse is detected.
- Assert no token in the revoked family remains usable, including a successor created by the winning exchange. Merely calling revokeFamily is insufficient evidence if subsequent verification ignores family revocation.
- Make the conditional consume, successor creation and revocation semantics explicit. Include a failure-path check showing partial failures cannot leave multiple valid successors or roll back the required revocation.
- Retain separate cookie and endpoint-access checks. Authenticated, public and service-authenticated routes should be valid under their declared contracts.

This is a proposed verification requirement, not a claim that these checks ran.

## #466 — Valid, add missing acceptance scenarios

[Issue #466](https://github.com/lowqualityloey/promptkit-os/issues/466)

The source defects remain at the current revision. The existing acceptance criteria address contrast and tier/stack behavior, but do not explicitly establish reduced-motion behavior or the approved text-only strategy. The listed findings are useful closure items; make the observable outcomes explicit.

Recommended additions:

- Enumerate the intended normal-text foreground/background pairs, separately for light and dark themes. Require the stated ratio without rounding up. Do not impose a text contrast requirement indiscriminately on decorative hairlines or all possible token combinations.
- With prefers-reduced-motion enabled, the reference component's enter/exit animations and transitions are disabled or use the documented reduced behavior; verify the actual example, not just token variables.
- Approved text-only navigation passes without inserting icons. Where icons exist, family consistency still applies.
- Specify the D0 note, D1 component, D2 surface and D3 system completion obligations, including N/A for non-React items, so the fix does not create new ambiguity between tiers.

## #467 — Valid, remove the invented prerequisite and expand scenario coverage

[Issue #467](https://github.com/lowqualityloey/promptkit-os/issues/467)

The parenthetical 'Needs a definitional ruling first: evidence-bearing vs decorative cards' is unnecessary. protocols/telemetry-cards.md:162 already defines status-cards: off as suppressing the decorative card while preserving genuine halts. Evidence recording can continue without showing the card. Treating this as unresolved delays a straightforward consistency correction.

The aggregate AC also omits explicit outcomes for the unsupported PR flags and profile-write authority. 'All are conditional-wording class fixes' understates the command and state-reconciliation changes.

Recommended closure matrix, one row per finding:

1. Corrected ordinary/draft PR creation commands use supported flags and capture a real returned URL.
2. status-cards: off suppresses cards without suppressing evidence or genuine halts.
3. A documentation delta persists intake evidence without an unapproved profile mutation; explicit human instructions retain their authority.
4. Task A's merge while B is active preserves B's working set and reconciles A's canonical Task Record before projecting completion into STATE.
5. A successful artifact-appropriate documentation verification satisfies the PR evidence gate without fabricating tests/typecheck evidence.
6. Disabled TDD does not mandate a pre-implementation RED phase; enabled TDD retains it.
7. The delegated verifier can audit each assigned claim using bounded supplied evidence and identify missing evidence explicitly.

Keeping one umbrella issue is reasonable, but use separate commits or subissues if checkpoint state reconciliation grows beyond the wording changes. The flags are unsupported on gh pr create; avoid saying they exist 'only' on view/status, since other CLI commands also support JSON output.
