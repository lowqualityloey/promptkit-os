## Actionable finding

### R1 — [P2] Provide an actual client/server module split

**Changed location:** [docs/recipes/env-validation.md:67–68](https://github.com/lowqualityloey/promptkit-os/blob/18dee14335dedbe51960c094a303f6fa156b07ca/docs/recipes/env-validation.md#L67-L68).

Pattern A puts `clientEnv()` and the eager server `env` initializer in one executable code fence. Filename comments at lines 59 and 67 do not form module boundaries. Copying this canonical block into the still-recommended `src/env.ts` and importing `clientEnv` in browser code evaluates the server initializer, which validates `DATABASE_URL` and `SESSION_SECRET` against the browser environment and throws even when the public bindings are configured correctly.

Splitting the fence at those comments also does not produce complete modules: the schemas and `parseOrExit` helper are declared above them without exports, and the server section has no imports for those declarations or `clientEnv`. Framework startup guidance at lines 84 and 86 still targets `src/env.ts`.

**Correction:** Show complete separate client and server modules with explicit imports. Keep the server schema and eager server validation outside the client import graph; provide a client-safe shared parser if needed. Update startup imports to the corresponding server validator path. This closes the remaining F17 boundary defect.

The literal `process.env.NEXT_PUBLIC_*` reads themselves correctly support browser inlining. [Next.js documentation](https://nextjs.org/docs/pages/guides/environment-variables) describes the direct-member requirement and the exclusion of dynamic lookups.
