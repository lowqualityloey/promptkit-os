## F17 — Next.js client env accessor: direction correct, mechanism under-specified

The defect is real and matches audit F17. `createEnv()` (env-validation.md:47–56) does `merged.safeParse(process.env)` and `export const env = createEnv()` (line 58), so importing the module in a browser component runs the client schema against an object whose `NEXT_PUBLIC_*` entries are `undefined` after bundling — Next.js only substitutes statically-analyzable `process.env.NEXT_PUBLIC_FOO` member expressions, not dynamic indexing of `process.env`.

Amend before implementing:

- **Bindings must be literal and statically analyzable.** The correction says "explicit `NEXT_PUBLIC_*` key bindings" but does not forbid the tempting shortcut of a loop/`Object.fromEntries(Object.keys(...))` helper. That would reintroduce the exact defect. State that each public value must be a direct `process.env.NEXT_PUBLIC_X` expression in the client input object.
- **Show the server/client split, not just the accessor.** The current recipe uses one merged schema and one module. The correction should require two modules (e.g. a client-only accessor that imports no server-only dependency, and a server accessor that composes client + server), because importing the merged module from a client component is what pulls `SESSION_SECRET` validation into the browser graph.
- **Acceptance needs browser-build evidence.** The issue's criterion ("provides a client-safe accessor with explicit `process.env.NEXT_PUBLIC_*` references, isolated from server secrets") is satisfied by *reading the recipe*. The prior review already required that the bindings "validate in a real browser build without requiring server secrets or importing server-only validation dependencies"; reference/string checks do not establish that. Keep that requirement.

## F18 — Stripe adapter: remediation valid, verification seam unspecified

The defect is real and matches audit F18. Pattern A (`verifyHmacSignature`, lines 41–49) computes a **bare** `sha256` hex digest over `rawBody`. Stripe instead sends `t=<ts>,v1=<sig>`, signs `"<ts>.<rawBody>"`, and permits multiple `v1` values within a tolerance window. Feeding the raw `stripe-signature` header into that helper compares unequal-length/unequal-content strings and rejects **every** valid delivery. The Next.js adaptation (103–106) even comments `// ...verify and dispatch`, i.e. it never shows the required scheme.

The proposed correction (document `stripe.webhooks.constructEvent(rawBody, signature, secret)` and route the verified event directly to ledger/enqueue, bypassing the bare-HMAC gate) is right. Amend before implementing:

- **Name the reuse seam, don't just name the API.** The current `handleWebhook` (56–94) couples verification, `JSON.parse`, `eventId` extraction, and ledger/enqueue. `constructEvent` both verifies *and* returns a typed event, so the corrected example should show a shared ledger/enqueue core that accepts an already-verified `{ eventId, payload }`, with the generic-HMAC and Stripe paths as two thin front-ends. Otherwise an implementer may "fix" it by pasting `constructEvent` into a function that still re-enters the bare gate.
- **Take `eventId` from the constructed event.** The generic path reads `eventId` from `payload.id`; the Stripe path must use the verified `event.id` (not a re-parse of an unverified body) and must not enqueue on a verification failure.
- **State the scheme of the generic helper.** The correction should say the helper supports a *single* `<prefix><hex>` digest (e.g. GitHub-style `sha256=`), so the two schemes are explicitly distinguished.

## F19 — Cobalt focus token: correct for one surface, under-scoped for the rest

The claim for the light Cobalt ring is accurate. `--ring: oklch(52% 0.22 250 / 0.35)` on the white card composites (sRGB space) to ≈ 1.71:1 — below the 3:1 SC 1.4.11 floor and below the 2.442:1 ceiling the issue cites for 35%-opaque any-color on white (independently reproduced; see appendix). The suggested opaque replacements also check out: `#2563eb` = 5.169:1, `#1d4ed8` = 6.702:1.

Two substantive gaps mean the issue does **not** cover F19's real breadth:

1. **The dark Cobalt ring fails too.** `--ring: oklch(64% 0.21 248 / 0.4)` over the dark card `oklch(18% 0.018 245)` = **1.877:1** (and ≈1.98:1 against the dark canvas) — the same SC 1.4.11 failure, untouched by the brief and by acceptance criterion 3, which only mentions "against white backgrounds".
2. **The Hum preset has the identical defect.** `--ring: oklch(50% 0.16 42 / 0.35)` (line 161) over its near-white card = **1.779:1**; the dark Hum ring `oklch(68% 0.15 45 / 0.4)` (line 176) is the same alpha pattern. Both presets ship the anti-pattern, so fixing only "Cobalt … against white" leaves the class unfixed.

Also amend:

- **Fit the replacement to the preset's own token.** The preset's `--primary` is `oklch(52% 0.22 250)` ≈ `#0065e0`, and its **opaque** form on white is already 5.333:1 — so the minimal, identity-preserving fix is to drop the alpha on the existing color, not to introduce `#2563eb`/`#1d4ed8` (Tailwind blue-600/700), which are a different hue than the preset's cobalt and would sit outside the token scale the spec's own anti-slop rule requires ("All colors must derive strictly from the tokens below"). If a specific hex is mandated it must be reconciled with `--primary`.
- **Cover every adjacent surface, not just white.** The ring can render against `--background`, `--surface-subtle`, and `--surface-card`; state the verification surface(s) and, if the ring is the *sole* authored cue, verify ≥3:1 against each. (This echoes the audit's "or another qualifying focus indicator" — an opaque ring, an outline, or a shape/offset cue are all acceptable; the issue narrows to "opaque token".)
- **An offset alone does not help.** The prior review already noted this; keep it, because a ring on white with a white offset gap still fails.

## Required amendments before implementation

1. **F17:** require literal `process.env.NEXT_PUBLIC_*` bindings and a client/server module split; add browser-build + negative-case evidence.
2. **F18:** specify the verified-event seam (shared ledger core taking an already-verified event), `event.id` as the source of `eventId`, and the generic helper's scheme; add expired/tampered/duplicate/no-side-effect acceptance cases.
3. **F19:** expand scope from "Cobalt against white" to **both presets, both color modes, and all ring-adjacent surfaces**; prefer de-alphaing the preset's own `--primary` over introducing off-scale hexes; keep "offset alone does not help".
4. **Criteria:** add at least one executable check for each fix (a token-contrast assertion, an env browser-build check, a webhook verify/no-op check) — the F17/F18/F19 recipes currently have no behavioral harness in `scripts/tests/`.
5. **Token budget:** `validate-playbooks.sh` enforces a hard ≤1500-token (bytes/4) ceiling. Current usage is env-validation **984** and webhook-idempotency **1258**, so the Stripe and accessor code must stay within ~516 and ~242 tokens respectively or the contract tests fail.

## Recommended delivery

Split into two reviewable PRs under #481: (a) recipes — env accessor (F17) + Stripe adapter (F18), sharing the ledger/enqueue seam; (b) design tokens — presets focus ring (F19) across both presets and modes, with a contrast note. A single PR is acceptable only if all three fixes carry behavior/contrast evidence.
